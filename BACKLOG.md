# Backlog — moved to GitHub Issues (2026-09-06)

The backlog now lives in **GitHub Issues**: https://github.com/ugurozsahin/sky-academy/issues

- **Order**: the **priority labels**, not a list (#94). A run takes the highest `priority:*` open issue labelled `routine-ok` that it can act on, oldest issue first within a priority; the exact query, and the three documented ways past it, are in `docs/ROUTINE-PROMPT.md` STEP 3. The hand-maintained ordered list that used to sit in a pinned issue was retired on 2026-09-11 (#94): a second source of truth has to agree with the labels, the board and reality, and repeatedly did not. **The project board stays as the owner's control surface and view**: he changes what happens next by changing an issue's priority, and #87's sync (`scripts/board-sync.mjs`, a launchd job on the owner's Mac every 15 minutes, pulse in the `board: heartbeat` issue) keeps the board's Status and Priority derived from the labels, the PR list and the branches — the rule table is the comment at the top of that script. Nothing in the routine's flow reads the board — a cloud session cannot reach Projects v2 at all (the cloud GitHub proxy answers non-PR GraphQL 403 whatever token it holds), and a board-driven routine would not know what to work on the day the Mac job stops. Labels are readable with the credentials every actor here already has.
- **Labels**: `priority:P0/P1/P2/P3` (P0 outranks P1 — the ordering `docs/ROUTINE-PROMPT.md` STEP 3 and `scripts/board-sync.mjs`'s `PRIORITIES` array both use), `owner-input` (needs the owner's art/decision), `routine-ok` (the dev routine may take it), `owner-approval` (on a PR: blocks the merge until the owner writes `OWNER: APPROVED`; only for a genuinely new look), `later` (parked), `blocked` (cannot move until another issue or a decision lands — it is what puts a card in the board's Blocked column, #87), plus area labels (`mode`, `curriculum`, `art`, `reward`, `platform`, `playtest`, `review`, `perf`, `debt`, `tests`).
- Label `frozen` is **retired**: the freeze it parked work for is over (below). It is not a way to park work — `later` is. No issue may carry it again — enforced in code, not just this prose (`.claude/rules/governance.md`, #101).
- **The code-health freeze is over (owner, 2026-09-10).** From 2026-09-06 the owner held a freeze: no new feature work while any issue labelled `review` or `debt` was open. Its condition is met — every `review`/`debt` issue the 6 September code review produced is now closed, the last four of them on 2026-09-10 — and he lifted it in session that day; the decision is recorded on issue #36. **The lift is a one-time event, not a condition that can re-arm:** a `review` or `debt` issue filed from now on does not re-impose it, and no run reinstates a freeze on its own — declaring one is the owner's, and it would be written into all three of these files at once. Work is chosen by the priority labels — highest `priority:*` first, oldest issue first within a priority — with no blanket bar on features: a `review`- or `debt`-labelled finding is ordered by its priority label like any other issue instead of blocking everything. What made the freeze work stays — review and QA by a different agent, the guard rails, and budget numbers that only go down. (Same wording in CLAUDE.md and docs/ROUTINE-PROMPT.md — change all three together; the rail in `tests/unit/guardrails.test.ts` checks they agree.)
- **Records have readers (#98).** `WORKLOG.md` is archived under `docs/worklog/` and nothing appends to it again — it had twelve-plus writers a day and no readers *by rule*, and it grew until a run died reading it. The test for any record is **who opens this, and when?** If there is no answer, do not write it. A change and why, including what was deliberately *not* done → the PR body. A decision that binds future work → the issue it came from, or `docs/decisions/NNN-title.md`. Operational state — last run, each check and its verdict, anomalies not acted on → the `routine: heartbeat` issue body, **overwritten every run, never appended**. History → `git log` and the PR list. A run's state lives in the issue labels, the open PRs and its heartbeat issue. (Same wording in `CLAUDE.md` and `docs/ROUTINE-PROMPT.md` — change all three together; a rail in `tests/unit/guardrails.test.ts` holds them to it and fails if `WORKLOG.md` returns to the repository root.)
- **Guard rails**: `tests/unit/guardrails.test.ts` and the `guard rail:` e2e tests turn past incidents into failing checks. Budgets go down, never up.
- **A stale review block may be adopted (#161).** A `REVIEW: CHANGES REQUESTED` block may be cleared by an agent that did not open the pull request when all four of these hold: the block is **at least 4 hours old**; the session that set it has posted **no comment on that same pull request in the last 2 hours** (a comment elsewhere in the repository does not protect the block — it is the signal that the reviewer has moved on); the adopting agent has re-derived the original objection against the current head and found it genuinely resolved; and its `REVIEW: CLEARED` comment says in its own first lines that it is clearing another reviewer's block and names the conditions that made that legitimate. (Its own session-URL requirement is in `.claude/rules/governance.md`, #191.) Clearing your own block is still forbidden, and so is clearing a live reviewer's; if you disagree with the original objection you do not clear it — you say so and leave it standing, or replace it with your own. A block never expires by itself — `review-gate` keeps reporting it until someone clears it deliberately — and a block whose comment carries no session URL cannot be adopted at all (`docs/ROUTINE-PROMPT.md` STEP 2 has the two mechanical checks).
- **Every comment and issue a session writes here carries its own `Session: https://claude.ai/code/session_<id>` line, not only a `REVIEW: CHANGES REQUESTED`/`REVIEW: CLEARED` comment (#199).** A fix-push comment, a status note, an issue body, an issue comment, a pull request body — all of it, going forward. The CLI's own auto-generated `_Generated by Claude Code (session_<id>)_` footer is not a substitute: it names whichever session's tool call produced the post, not necessarily the session responsible for the words above it, and a plain API call carries no such footer at all — which is how PR #178's and PR #187's fix-push comments shipped with no session marker whatsoever and had to be patched by hand once found. This is documentation only, the same as #191 was for the clearing side: it does not change what `review-gate` gates, and it is not retroactive.
- **A comment or issue states its point up front, not only its signature (#200).** The floor for every one of them: say in the first line or two what it is and why it matters right now, then close with the `Session:` line above — nothing forces a heading onto a one-line status note, but the note has to actually say its point rather than assume the reader infers it. A fix-push comment additionally opens `Pushed <sha>, addressing <what>`, answers each blocking finding by the review's own numbering, states the tests it ran, and closes `Ready for re-review` — never `REVIEW: CLEARED`, which stays the reviewer's own mark. An issue proposing a fix additionally states the problem with real evidence, a `## Proposed fix` section, and a `## What this deliberately does not do` section — the same two-sided shape `open-pr/SKILL.md` §3 already asks of a pull request body, written down for issues too rather than left to happen to match by habit.
- **A run with nothing to review may take a second item (#97)** — the owner's, in session on 2026-09-10 — as a **second, separate pull request**, never one pull request closing two issues, and never a third item. All four conditions must hold: **(1)** no open pull request is waiting for a review that run could do — one it opened itself, one blocked by a `REVIEW: CHANGES REQUESTED` it may not clear, and one held only by an unanswered `owner-approval` are not "waiting", and the condition is *not* "no open pull requests at all"; **(2)** the ~45-minute clock, measured from the start of the run rather than from the second item, has not run out; **(3)** the second item's files are disjoint from the first's, tested against the first PR's changed-file list; **(4)** the first item actually finished — a WIP `Part of #<n>` push does not count. It is a **condition, not a quota**: the moment second items produce a backlog, condition 1 stops being true by itself and the run goes back to reviewing — no counter, no rota, no "two items per run" allowance. The run's heartbeat snapshot must say whether it took one and, if not, which condition failed — enforced in code, not just this prose (`.claude/rules/governance.md`, #97/#239). (Same four conditions in `CLAUDE.md` and `docs/ROUTINE-PROMPT.md`, whose STEP 3 has the mechanical version — change all three together; a rail in `tests/unit/guardrails.test.ts` checks they agree.)
- **Workflow** (minimum scrum, in every issue): Refine → Develop (agent A, branch `feature|fix|chore/<n>-<slug>` — `fix/` for `bug`/`playtest`, `feature/` for `enhancement`, `chore/` for everything else (#89); the prefix follows the label describing the *change*, not the one describing where it was found, and the slug is lower case, hyphens, a few words. The old `claude/*` names are retired: they said nothing about the work, so a branch listing could not be read and a stale branch could not be judged without opening its PR. Nothing finds work by branch prefix any more — **list every open PR, never a `claude/*` prefix match**. Merged branches delete themselves (`delete_branch_on_merge` is on for the repository since 2026-09-10), so no run adds a cleanup step. PR titled `(#<n>)` with `Closes #<n>` in the body — `Part of #<n>` instead when part of the issue is deferred, or GitHub closes it early. **A closing keyword next to an issue reference closes that issue wherever it sits in the body — including inside a sentence denying it (#83).** "Left open so merging this does not close #<n>" is how PR ugurozsahin/sky-academy-private-archive#139 shut issue 44 while explaining that it must not: GitHub scans the whole body for `close`/`fix`/`resolve` and their forms followed by `#<n>` or the issue's URL, and has no notion of negation, quotation or context. Say "the issue stays open" instead; break the link (`#&#8203;<n>`, or "issue 44" in words) when the keyword is unavoidable; and check what you actually wrote with `node scripts/review-gate.mjs body.md`, which prints the issues that body would close.) → Review (a *different* agent) → QA (the reviewer, e2e + screenshots — **mobile by default, the project CI runs on a PR; the full matrix is the nightly's**, #81, and **CI runs e2e on a PR only when the diff can reach the game**, #96 — every PR still gets a `CI` check, so a missing one is never expected) → Owner action → Done (merged, issue closed). Merging no longer reaches the live artifact: the publisher task was stood down on 2026-09-09 and nothing republishes in its place.
