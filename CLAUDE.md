# Sky Ninja Academy — project context

Slice-the-answer learning game for UK Reception / Year 1 / Year 2. Mobile-first, also desktop. English only.
Owner priorities: playability, fun, visuals must look professional (art supplied by owner), tests at every step, low token use. **His approval is for a NEW look only** — art, skins, a redesigned effect, anything answering "do you like it". Work whose acceptance criterion is that the look must *not* change is verified with before/after evidence by the reviewer, never sent to him. When a change does need him: label the PR `owner-approval`; he replies `OWNER: APPROVED` or `OWNER: REJECTED — reason`, and `review-gate` holds the PR red until he does. No agent ever writes those markers.

## Stack
Vite + vanilla TypeScript (no framework), canvas arena, DOM HUD, localStorage. Vitest (unit) + Playwright (e2e, mobile + desktop projects; **a pull request runs mobile only, the nightly runs the full matrix** — #141, **and a pull request runs e2e at all only when its diff can reach the game** — #176: `src/`, `index.html`, `public/`, `tests/e2e/`, `playwright.config.*`, `package*.json`, `ci.yml`. Unit tests and the build run on every pull request including a docs-only one, because the guard rails *are* documentation checks; the e2e step is skipped visibly, never the whole workflow, so no pull request is ever without a `CI` check.)
`npm run dev` · `npm test` · `npm run build` · `npm run test:e2e` · `npm run test:all` · `node scripts/bundle-single.mjs` (single-file build) · APK: GitHub Actions "Android APK" (`docs/ANDROID.md`).

## Rules
- Every topic generator must pass `tests/unit/curriculum.test.ts` (answer in options, unique options, arithmetic verified, KS1 ranges). Add a topic = add generator + registry entry (see `.claude/skills/add-topic`).
- Difficulty 1/2/3 = mission stages. Reception is "gentle" (missed bubbles cost no life). Keep numbers within NC ranges (R ≤10, Y1 ≤20, Y2 ≤100).
- `window.__sna` hooks (`answer()`, `wrong()`, `bubbles()`, `state()`) are the e2e contract — keep them working.
- Don't add dependencies without reason (Capacitor for the Android APK is the one exception — see `docs/ANDROID.md`; `android/` is generated, only touch it via `npx cap`/`scripts/android-assets.py`); no external assets except Google Fonts (Fredoka) and `public/avatars`.
- Keep files small; prefer editing existing modules over new abstractions. Run `npm test` after logic changes, `npm run test:e2e` after UI changes (mobile is the default project a PR is judged on — run desktop too when a change could be viewport-sensitive, since nothing else will until that night).
- **The code-health freeze is over (owner, 2026-09-10).** From 2026-09-06 the owner held a freeze: no new feature work while any issue labelled `review` or `debt` was open. Its condition is met — every `review`/`debt` issue the 6 September code review produced is now closed, the last four of them on 2026-09-10 — and he lifted it in session that day; the decision is recorded on issue #36. **The lift is a one-time event, not a condition that can re-arm:** a `review` or `debt` issue filed from now on does not re-impose it, and no run reinstates a freeze on its own — declaring one is the owner's, and it would be written into all three of these files at once. Work is chosen by issue #46's order and the priority labels, with no blanket bar on features: a `review`- or `debt`-labelled finding is ordered by its priority label like any other issue instead of blocking everything. What made the freeze work stays — review and QA by a different agent, the guard rails, and budget numbers that only go down. The owner's reason for the ordering, worth keeping: the refactors had to finish *before* feature work restarted, because refactors move code around and features written first would have conflicted with them. `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` carry this same wording — change all three together, and `tests/unit/guardrails.test.ts` holds them to it.
- **Guard rails** (`tests/unit/guardrails.test.ts` + the `guard rail:` tests in the e2e spec) encode mistakes we have already made — render frame rate, screen teardown on a route change, screen-class CSS collisions, `as any` in game logic, comparator shuffles, `shadowBlur`, the dependency allowlist, listener pairing; British English lives in `british.test.ts`. They are text/DOM checks, not proofs: they catch the exact spellings and the exact screens named in their comments. A *budget* rail records existing debt: lower the number when you remove a case, **never raise it to go green**. Adding a rail with each bug fix is part of the fix. `.github/workflows/ci.yml` runs all of it on every PR.
- **Governance PRs** (this file, `BACKLOG.md`, `docs/ROUTINE-PROMPT.md`, the workflows, the guard rails) state in one line whether they **tighten** the constraints on a run or **loosen** them. Tightening — and describing behaviour that already exists — is ordinary work, reviewed and merged like anything else. Loosening is owner-gated and never routine-merged. Judge the constraint, not the signal: *after this change, is there still something red that a merge rule reads?* `docs/ROUTINE-PROMPT.md` has the full rule.
- **How a review blocks a merge here:** one GitHub token serves every agent and the owner, so every PR looks self-authored and GitHub refuses a formal CHANGES_REQUESTED review — a reviewer therefore marks the PR **draft** and begins its comment `REVIEW: CHANGES REQUESTED`, and those two marks are the entire mechanism. Only the reviewer who set them clears them — with a `REVIEW: CLEARED` comment and "Ready for review"; pushing a fix does not clear a review, and nobody undrafts a PR to get past one, their own included. `.github/workflows/review-gate.yml` reads both marks and fails the `review-gate` check while a block stands, so a blocked PR is red rather than merely commented on. **Clearing a block re-runs CI** — `ci.yml` subscribes to `ready_for_review` (#159) — so the undraft fires a fresh run against the current merge ref and the merge waits for *that* run: an older green on the same head SHA is evidence about a tree `main` has since moved past, which is how #150 was merged on a tick four merges stale. This applies to any session doing a review, not only the dev routine.
- The dev routine's own instructions live in `docs/ROUTINE-PROMPT.md` — the routine's stored prompt is only a bootstrap that reads that file, so changing how the runs behave is a normal PR. It runs **every two hours** (cron `37 */2 * * *`); the trigger is still named "…— hourly dev run" from when it fired hourly, so take the cadence from the cron, not the name. Backlog lives in **GitHub Issues** (see `BACKLOG.md` for the labels). Order = issue #46, owner-maintained; never reorder it. Every issue carries the scrum checklist: Develop (branch `claude/issue-<n>` or the run's assigned push branch, PR titled `(#<n>)` with `Closes #<n>` in the body — `Part of #<n>` instead when part of the issue is deferred, or GitHub closes it early. **A closing keyword next to an issue reference closes that issue wherever it sits in the body — including inside a sentence denying it (#144).** "Left open so merging this does not close #<n>" is how PR #139 shut issue 44 while explaining that it must not: GitHub scans the whole body for `close`/`fix`/`resolve` and their forms followed by `#<n>` or the issue's URL, and has no notion of negation, quotation or context. Say "the issue stays open" instead; break the link (`#&#8203;<n>`, or "issue 44" in words) when the keyword is unavoidable; and check what you actually wrote with `node scripts/review-gate.mjs body.md`, which prints the issues that body would close.) → Review + QA by a *different* agent (spawn a fresh subagent, or leave it to the next routine run) → Owner action → Done (merged, issue closed). **Records have readers (#178).** `WORKLOG.md` is archived under `docs/worklog/` and nothing appends to it again — it had twelve-plus writers a day and no readers *by rule*, and it grew until a run died reading it. The test for any record is **who opens this, and when?** If there is no answer, do not write it. A change and why, including what was deliberately *not* done → the PR body. A decision that binds future work → the issue it came from, or `docs/decisions/NNN-title.md`. Operational state — last run, each check and its verdict, anomalies not acted on → the `routine: heartbeat` issue body, **overwritten every run, never appended**. History → `git log` and the PR list. A run's state lives in #46, the open PRs and its heartbeat issue. (Same wording in `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` — change all three together; a rail in `tests/unit/guardrails.test.ts` holds them to it and fails if `WORKLOG.md` returns to the repository root.) One scheduled task runs beside the dev routine: the **watchdog** every 6 hours (cron `0 5,11,17,23 * * *`, `docs/WATCHDOG-PROMPT.md`) watches for the things a routine cannot check about itself and opens `watchdog` issues. There used to be a second — the **artifact publisher**, which republished the single-file build of main to the live artifact (https://claude.ai/public/artifacts/43914c31-28c5-4afb-bf15-966a64e09668) — but the owner stood it down on 2026-09-09, so that artifact is frozen and drifts from main by design. No agent publishes it instead. Never review your own PR.
