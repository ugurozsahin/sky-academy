# Sky Ninja Academy — project context

Slice-the-answer learning game for UK Reception / Year 1 / Year 2. Mobile-first, also desktop. English only.
Owner priorities: playability, fun, visuals must look professional (art supplied by owner), tests at every step, low token use. **His approval is for a NEW look only** — art, skins, a redesigned effect, anything answering "do you like it". Work whose acceptance criterion is that the look must *not* change is verified with before/after evidence by the reviewer, never sent to him. When a change does need him: label the PR `owner-approval`; he replies `OWNER: APPROVED` or `OWNER: REJECTED — reason`, and `review-gate` holds the PR red until he does. No agent ever writes those markers.

## Stack
Vite + vanilla TypeScript (no framework), canvas arena, DOM HUD, localStorage. Vitest (unit) + Playwright (e2e — mobile-only on a pull request, full matrix on the nightly, skipped when a diff can't reach the game; #81, #96, `.claude/rules/e2e.md`).
`npm run dev` · `npm test` · `npm run build` · `npm run test:e2e` · `npm run test:all` · `node scripts/bundle-single.mjs` (single-file build) · APK: GitHub Actions "Android APK" (`docs/ANDROID.md`).

## Layout (read only what you need)
- `src/curriculum/` — `types.ts` (Question/Topic model, YEARS), `maths.ts`, `writing.ts` (pure generators `(difficulty, rng) => Question`), `util.ts` (numQ/wordQ/distractors), `index.ts` (registry). See `docs/CURRICULUM.md` for the NC map.

- `src/avatars.ts` (roster, `fx` element style, praise lines; art in `public/avatars/*.webp`), `src/audio.ts` (synth SFX + speech), `src/storage.ts`, `src/style.css`.
- `tests/unit/*.test.ts`, `tests/e2e/game.spec.ts`, `scripts/` (screenshots, single-file bundle, art extraction).

## Rules

- Game arena / play-screen rules, including the `window.__sna` e2e contract → `.claude/rules/game.md` (`src/game/**`, `src/ui/play.ts`) (#101).
- e2e conventions (helpers, the compile check, mobile-vs-nightly split) → `.claude/rules/e2e.md` (`tests/e2e/**`, `playwright.config.*`) (#101).
- Visual style and UI conventions → `.claude/rules/style.md` (`src/style.css`, `src/ui/**`) (#101).
- Don't add dependencies without reason; no external assets except Google Fonts (Fredoka) and `public/avatars`. Android/Capacitor → `.claude/rules/android.md` (`android/**`, `capacitor.config.ts`) (#101).
- Keep files small; prefer editing existing modules over new abstractions. Run `npm test` after logic changes, `npm run test:e2e` after UI changes (mobile is the default project a PR is judged on — run desktop too when a change could be viewport-sensitive, since nothing else will until that night).
- **The code-health freeze is over (owner, 2026-09-10).** The lift is a **one-time event, not a condition that can re-arm**: a `review`/`debt` issue filed from now on does not re-impose it, and no run reinstates a freeze on its own. Work is chosen by the **priority labels** — highest first, oldest within a priority — with no blanket bar on features. `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` carry this same wording; `.claude/rules/governance.md` has the reasoning and history.
- **Guard rails** (mistakes already made, the budget-rail rule, what `scripts/` holds) → `.claude/rules/guardrails.md` (`tests/unit/guardrails.test.ts`, `scripts/**`) (#101). `.github/workflows/ci.yml` runs all of it on every PR.
- **Skills and review agents are vendored into `.claude/`**, pinned to the commit they came from — the allow-list in `tests/unit/guardrails.test.ts` is the full list and the enforcement; a skill or agent it does not name fails the build. `frontend-design` is gated to issues labelled `new-ui`; every other UI change follows `design-language` alone.
- **Governance PRs** (this file, `BACKLOG.md`, `docs/ROUTINE-PROMPT.md`, the workflows, the guard rails) state in one line whether they **tighten** or **loosen** the constraints on a run. Tightening is ordinary work, merged like any other; loosening is owner-gated, never routine-merged. See `.claude/rules/governance.md` and the `open-pr` skill §6.
- **A review blocks a merge by draft + comment**, since one GitHub token serves every agent and the owner and GitHub refuses a formal CHANGES_REQUESTED review here: a reviewer marks the PR draft and begins a comment `REVIEW: CHANGES REQUESTED`; the reviewer who set it clears it with `REVIEW: CLEARED` and "Ready for review", which re-runs CI (#88). **A stale review block may be adopted (#161).** A `REVIEW: CHANGES REQUESTED` block may be cleared by an agent that did not open the pull request when all four of these hold: the block is **at least 4 hours old**; the session that set it has posted **no comment on that same pull request in the last 2 hours** (a comment elsewhere in the repository does not protect the block — it is the signal that the reviewer has moved on); the adopting agent has re-derived the original objection against the current head and found it genuinely resolved; and its `REVIEW: CLEARED` comment says in its own first lines that it is clearing another reviewer's block and names the conditions that made that legitimate. When that REVIEW: CLEARED comment is the adoption itself, it carries the clearing session's own URL too. Clearing your own block is still forbidden, and so is clearing a live reviewer's. A block never expires by itself — `review-gate` keeps reporting it until someone clears it deliberately. Full mechanics (the two mechanical checks, what counts as "moved on") → `.claude/rules/governance.md` and the `review-pr` skill.
- **Every comment and issue a session writes here carries its own `Session: https://claude.ai/code/session_<id>` line, not only a `REVIEW: CHANGES REQUESTED`/`REVIEW: CLEARED` comment (#199).** A fix-push comment, a status note, an issue body, an issue comment, a pull request body — all of it, going forward. The CLI's own auto-generated `_Generated by Claude Code (session_<id>)_` footer is not a substitute: it names whichever session's tool call produced the post, not necessarily the session responsible for the words above it, and a plain API call carries no such footer at all — which is how PR #178's and PR #187's fix-push comments shipped with no session marker whatsoever and had to be patched by hand once found. This is documentation only, the same as #191 was for the clearing side: it does not change what `review-gate` gates, and it is not retroactive.
- **A comment or issue states its point up front, not only its signature (#200).** The floor for every one of them: say in the first line or two what it is and why it matters right now, then close with the `Session:` line above — nothing forces a heading onto a one-line status note, but the note has to actually say its point rather than assume the reader infers it. A fix-push comment additionally opens `Pushed <sha>, addressing <what>`, answers each blocking finding by the review's own numbering, states the tests it ran, and closes `Ready for re-review` — never `REVIEW: CLEARED`, which stays the reviewer's own mark. An issue proposing a fix additionally states the problem with real evidence, a `## Proposed fix` section, and a `## What this deliberately does not do` section — the same two-sided shape `open-pr/SKILL.md` §3 already asks of a pull request body, written down for issues too rather than left to happen to match by habit.
- **The dev routine's instructions live in `docs/ROUTINE-PROMPT.md`** — it changes between runs, so read it fresh every time, never from memory. Backlog lives in GitHub Issues (`BACKLOG.md` has the labels). Branches: `feature|fix|chore/<n>-<slug>` — `fix/` for `bug`/`playtest`, `feature/` for `enhancement`, `chore/` for everything else. PR title carries `(#<n>)`; body says `Closes #<n>` when finished, `Part of #<n>` when deferring — a closing keyword next to an issue number closes it wherever it sits in the body, negation included, so check with `node scripts/review-gate.mjs body.md`. **Records have readers**: the test for any record is **who opens this, and when?** A change and why → the PR body. A decision that binds future work → the issue, or `docs/decisions/NNN-title.md`. Operational state → the `routine: heartbeat` issue body, **overwritten every run, never appended**. History → `git log` and the PR list. Full flow, the priority query, the watchdog schedule → `docs/ROUTINE-PROMPT.md` and `.claude/rules/governance.md`. Never review your own PR.
- **A run with nothing to review may take a second item** — as a **second, separate pull request**, never one pull request closing two issues, and never a third item. It is a **condition, not a quota**: all four of (1) no open pull request is waiting for a review this run could do (and that condition is *not* "no open pull requests at all"); (2) the ~45-minute clock, measured from the start of the run, has not run out; (3) the second item's files are disjoint from the first's; (4) the first item actually finished. `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` carry the same rule; STEP 3 there has the mechanical version.
