# Sky Ninja Academy — project context

Slice-the-answer learning game for UK Reception / Year 1 / Year 2. Mobile-first, also desktop. English only.
Owner priorities: playability, fun, visuals must look professional (art supplied by owner), tests at every step, low token use. **His approval is for a NEW look only** — art, skins, a redesigned effect, anything answering "do you like it". Work whose acceptance criterion is that the look must *not* change is verified with before/after evidence by the reviewer, never sent to him. When a change does need him: label the PR `owner-approval`; he replies `OWNER: APPROVED` or `OWNER: REJECTED — reason`, and `review-gate` holds the PR red until he does. No agent ever writes those markers.

## Stack
Vite + vanilla TypeScript (no framework), canvas arena, DOM HUD, localStorage. Vitest (unit) + Playwright (e2e, mobile + desktop projects; **a pull request runs mobile only, the nightly runs the full matrix** — #81, **and a pull request runs e2e at all only when its diff can reach the game** — #96: `src/`, `index.html`, `public/`, `tests/e2e/`, `playwright.config.*`, `package*.json`, `ci.yml`. Unit tests and the build run on every pull request including a docs-only one, because the guard rails *are* documentation checks; the e2e step is skipped visibly, never the whole workflow, so no pull request is ever without a `CI` check.)
`npm run dev` · `npm test` · `npm run build` · `npm run test:e2e` · `npm run test:all` · `node scripts/bundle-single.mjs` (single-file build) · APK: GitHub Actions "Android APK" (`docs/ANDROID.md`).

## Rules
- Curriculum generator rules (answer/option checks, difficulty stages, NC ranges) → `.claude/rules/curriculum.md`, loaded when a session touches `src/curriculum/**` or `tests/unit/curriculum.test.ts` (#101).
- Game arena / play-screen rules, including the `window.__sna` e2e contract → `.claude/rules/game.md` (`src/game/**`, `src/ui/play.ts`) (#101).
- Don't add dependencies without reason; no external assets except Google Fonts (Fredoka) and `public/avatars`. Android/Capacitor → `.claude/rules/android.md` (`android/**`, `capacitor.config.ts`) (#101).
- Keep files small; prefer editing existing modules over new abstractions. Run `npm test` after logic changes, `npm run test:e2e` after UI changes (mobile is the default project a PR is judged on — run desktop too when a change could be viewport-sensitive, since nothing else will until that night).
- **The code-health freeze is over (owner, 2026-09-10).** From 2026-09-06 the owner held a freeze: no new feature work while any issue labelled `review` or `debt` was open. Its condition is met — every `review`/`debt` issue the 6 September code review produced is now closed, the last four of them on 2026-09-10 — and he lifted it in session that day; the decision is recorded on issue #36. **The lift is a one-time event, not a condition that can re-arm:** a `review` or `debt` issue filed from now on does not re-impose it, and no run reinstates a freeze on its own — declaring one is the owner's, and it would be written into all three of these files at once. Work is chosen by the priority labels — highest `priority:*` first, oldest issue first within a priority — with no blanket bar on features: a `review`- or `debt`-labelled finding is ordered by its priority label like any other issue instead of blocking everything. What made the freeze work stays — review and QA by a different agent, the guard rails, and budget numbers that only go down. The owner's reason for the ordering, worth keeping: the refactors had to finish *before* feature work restarted, because refactors move code around and features written first would have conflicted with them. `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` carry this same wording — change all three together, and `tests/unit/guardrails.test.ts` holds them to it.
- **Guard rails** encode mistakes we have already made; the mistake list, the budget-rail rule and what `scripts/` holds → `.claude/rules/guardrails.md` (`tests/unit/guardrails.test.ts`, `scripts/**`) (#101). `.github/workflows/ci.yml` runs all of it on every PR.
- **Agent skills and review agents are vendored into `.claude/` (#99).** A cloud session or a scheduled run sees only the skills in the cloned repository — a plugin needs an interactive install nobody is there to do — so they are copied in and **pinned to the commit they came from**: four skills from `obra/superpowers` (`verification-before-completion`, `using-git-worktrees`, `systematic-debugging`, `test-driven-development`) and three review agents from `anthropics/claude-plugins-official` (`pr-test-analyzer`, `silent-failure-hunter`, `type-design-analyzer`). A vendored body is never edited; an adjustment we need belongs in a project skill that refers to it. A reviewer runs the three agents on the diff and quotes what they find — **their findings are input to the review, never its verdict**: the reviewer still owns `REVIEW: CLEARED` / `REVIEW: CHANGES REQUESTED`, and no agent ever writes an `OWNER:` marker. The list in `tests/unit/guardrails.test.ts` is the allow-list, because a description costs context on every turn: a skill or an agent the list does not name fails the build. **`frontend-design`, vendored from the same marketplace, is gated**: it applies only to an issue labelled `new-ui` (a screen built from nothing, e.g. the onboarding wizard) — every other UI change follows `design-language` alone, and on any conflict between the two, `design-language` wins.
- **Governance PRs** (this file, `BACKLOG.md`, `docs/ROUTINE-PROMPT.md`, the workflows, the guard rails) state in one line whether they **tighten** the constraints on a run or **loosen** them. Tightening — and describing behaviour that already exists — is ordinary work, reviewed and merged like anything else. Loosening is owner-gated and never routine-merged. Judge the constraint, not the signal: *after this change, is there still something red that a merge rule reads?* The `open-pr` skill (§6) has the full rule.
- **How a review blocks a merge here:** one GitHub token serves every agent and the owner, so every PR looks self-authored and GitHub refuses a formal CHANGES_REQUESTED review — a reviewer therefore marks the PR **draft** and begins its comment `REVIEW: CHANGES REQUESTED`, and those two marks are the entire mechanism. The reviewer who set them clears them — with a `REVIEW: CLEARED` comment and "Ready for review"; pushing a fix does not clear a review, and nobody undrafts a PR to get past one, their own included. **A stale review block may be adopted (#161).** A `REVIEW: CHANGES REQUESTED` block may be cleared by an agent that did not open the pull request when all four of these hold: the block is **at least 4 hours old**; the session that set it has posted **no comment on that same pull request in the last 2 hours** (a comment elsewhere in the repository does not protect the block — it is the signal that the reviewer has moved on); the adopting agent has re-derived the original objection against the current head and found it genuinely resolved; and its `REVIEW: CLEARED` comment says in its own first lines that it is clearing another reviewer's block and names the conditions that made that legitimate. When that REVIEW: CLEARED comment is the adoption itself, it carries the clearing session's own URL too — the same footer, so a later reader is not left guessing which session cleared a stale block from an unmarked comment (#191). Clearing your own block is still forbidden, and so is clearing a live reviewer's; if you disagree with the original objection you do not clear it — you say so and leave it standing, or replace it with your own. A block never expires by itself — `review-gate` keeps reporting it until someone clears it deliberately — and a block whose comment carries no session URL cannot be adopted at all (`docs/ROUTINE-PROMPT.md` STEP 2 has the two mechanical checks). `.github/workflows/review-gate.yml` reads both marks and fails the `review-gate` check while a block stands, so a blocked PR is red rather than merely commented on. **Clearing a block re-runs CI** — `ci.yml` subscribes to `ready_for_review` (#88) — so the undraft fires a fresh run against the current merge ref and the merge waits for *that* run: an older green on the same head SHA is evidence about a tree `main` has since moved past, which is how ugurozsahin/sky-academy-private-archive#150 was merged on a tick four merges stale. This applies to any session doing a review, not only the dev routine.
- **Every comment and issue a session writes here carries its own `Session: https://claude.ai/code/session_<id>` line, not only a `REVIEW: CHANGES REQUESTED`/`REVIEW: CLEARED` comment (#199).** A fix-push comment, a status note, an issue body, an issue comment, a pull request body — all of it, going forward. The CLI's own auto-generated `_Generated by Claude Code (session_<id>)_` footer is not a substitute: it names whichever session's tool call produced the post, not necessarily the session responsible for the words above it, and a plain API call carries no such footer at all — which is how PR #178's and PR #187's fix-push comments shipped with no session marker whatsoever and had to be patched by hand once found. This is documentation only, the same as #191 was for the clearing side: it does not change what `review-gate` gates, and it is not retroactive.
- **A comment or issue states its point up front, not only its signature (#200).** The floor for every one of them: say in the first line or two what it is and why it matters right now, then close with the `Session:` line above — nothing forces a heading onto a one-line status note, but the note has to actually say its point rather than assume the reader infers it. A fix-push comment additionally opens `Pushed <sha>, addressing <what>`, answers each blocking finding by the review's own numbering, states the tests it ran, and closes `Ready for re-review` — never `REVIEW: CLEARED`, which stays the reviewer's own mark. An issue proposing a fix additionally states the problem with real evidence, a `## Proposed fix` section, and a `## What this deliberately does not do` section — the same two-sided shape `open-pr/SKILL.md` §3 already asks of a pull request body, written down for issues too rather than left to happen to match by habit.
- The dev routine's own instructions live in `docs/ROUTINE-PROMPT.md` — the routine's stored prompt is only a bootstrap that reads that file, so changing how the runs behave is a normal PR. It runs **every two hours** (cron `37 */2 * * *`); the trigger is still named "…— hourly dev run" from when it fired hourly, so take the cadence from the cron, not the name. Backlog lives in **GitHub Issues** (see `BACKLOG.md` for the labels). Order = the priority labels: the highest `priority:*` open issue labelled `routine-ok`, not labelled `later`/`owner-input`/`owner-approval`, that nothing else is already solving — oldest first within a priority (#94; the full query is in `docs/ROUTINE-PROMPT.md` STEP 3). The project board is the owner's view of that, not a second list — nothing in the flow reads it. Every issue carries the scrum checklist: Develop (branch `feature|fix|chore/<n>-<slug>` — `fix/` for `bug`/`playtest`, `feature/` for `enhancement`, `chore/` for everything else (#89); the prefix follows the label describing the *change*, not the one describing where it was found, and the slug is lower case, hyphens, a few words. The old `claude/*` names are retired: they said nothing about the work, so a branch listing could not be read and a stale branch could not be judged without opening its PR. Nothing finds work by branch prefix any more — **list every open PR, never a `claude/*` prefix match**. Merged branches delete themselves (`delete_branch_on_merge` is on for the repository since 2026-09-10), so no run adds a cleanup step. PR titled `(#<n>)` with `Closes #<n>` in the body — `Part of #<n>` instead when part of the issue is deferred, or GitHub closes it early. **A closing keyword next to an issue reference closes that issue wherever it sits in the body — including inside a sentence denying it (#83).** "Left open so merging this does not close #<n>" is how PR ugurozsahin/sky-academy-private-archive#139 shut issue 44 while explaining that it must not: GitHub scans the whole body for `close`/`fix`/`resolve` and their forms followed by `#<n>` or the issue's URL, and has no notion of negation, quotation or context. Say "the issue stays open" instead; break the link (`#&#8203;<n>`, or "issue 44" in words) when the keyword is unavoidable; and check what you actually wrote with `node scripts/review-gate.mjs body.md`, which prints the issues that body would close.) → Review + QA by a *different* agent (spawn a fresh subagent, or leave it to the next routine run) → Owner action → Done (merged, issue closed). **Records have readers (#98).** `WORKLOG.md` is archived under `docs/worklog/` and nothing appends to it again — it had twelve-plus writers a day and no readers *by rule*, and it grew until a run died reading it. The test for any record is **who opens this, and when?** If there is no answer, do not write it. A change and why, including what was deliberately *not* done → the PR body. A decision that binds future work → the issue it came from, or `docs/decisions/NNN-title.md`. Operational state — last run, each check and its verdict, anomalies not acted on → the `routine: heartbeat` issue body, **overwritten every run, never appended**. History → `git log` and the PR list. A run's state lives in the issue labels, the open PRs and its heartbeat issue. (Same wording in `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` — change all three together; a rail in `tests/unit/guardrails.test.ts` holds them to it and fails if `WORKLOG.md` returns to the repository root.) One scheduled task runs beside the dev routine: the **watchdog** every 6 hours (cron `0 5,11,17,23 * * *`, `docs/WATCHDOG-PROMPT.md`) watches for the things a routine cannot check about itself and opens `watchdog` issues. There used to be a second — the **artifact publisher**, which republished the single-file build of main to the live artifact (https://claude.ai/public/artifacts/43914c31-28c5-4afb-bf15-966a64e09668) — but the owner stood it down on 2026-09-09, so that artifact is frozen and drifts from main by design. No agent publishes it instead. Never review your own PR.
- **A run with nothing to review may take a second item (#97)** — the owner's, in session on 2026-09-10 — as a **second, separate pull request**, never one pull request closing two issues, and never a third item. All four conditions must hold: **(1)** no open pull request is waiting for a review that run could do — one it opened itself, one blocked by a `REVIEW: CHANGES REQUESTED` it may not clear, and one held only by an unanswered `owner-approval` are not "waiting", and the condition is *not* "no open pull requests at all"; **(2)** the ~45-minute clock, measured from the start of the run rather than from the second item, has not run out; **(3)** the second item's files are disjoint from the first's, tested against the first PR's changed-file list; **(4)** the first item actually finished — a WIP `Part of #<n>` push does not count. It is a **condition, not a quota**: the moment second items produce a backlog, condition 1 stops being true by itself and the run goes back to reviewing, which is the property that must survive any future edit — no counter, no rota, no "two items per run". The run's heartbeat snapshot says whether it took one and, if not, which condition failed. `BACKLOG.md` and `docs/ROUTINE-PROMPT.md` carry the same rule (STEP 3 has the mechanical version) — change all three together, and `tests/unit/guardrails.test.ts` holds them to it.
